# v0.3.8 · Windows weight-reading stability fixes

## Fix the high-risk mapping path during text encoding

In a v0.3.7 512 text-to-image test on RTX 4070 Laptop 8 GB / 32 GB RAM, automatic streaming completed model initialization but then crashed natively with `0xC0000005` during text encoding. The exception address matched the vocabulary offset in the safetensors file; a separate rerun with the same configuration had succeeded. This evidence supports a Windows whole-file mapping failure, but the report alone does not establish that a `safe_open` context closed prematurely.

This release removes mapped reads from the app's streaming adapter:

- Checkpoint headers are indexed through ordinary file I/O, with checks for shapes, dtype, byte ranges, and file changes.
- The encoder vocabulary reads only the deduplicated rows needed for the tokens, preserving the original order and shape without copying the entire vocabulary. In a dedicated check using the real official file, 8 unique rows required only 64 KiB of payload reads, versus 1,244,659,712 bytes for the full embedding.
- DiT / text layers retain one CPU staging block and one GPU block, explicitly reading into owned tensors. Static weights and vision components also use owned storage.
- Before importing LightX2V / Transformers, the Windows worker selects `pread` for ordinary safetensors loading, bypassing PyTorch's whole-file COW storage path. Metadata initialization in the pinned safetensors version can still use a checked Rust mapping, so this does not justify claiming that all ordinary loading is completely mapping-free.

Windows copy-on-write mappings consume commit. Available physical RAM, system commit headroom, and VRAM are different metrics. Therefore, free physical RAM and the absence of CUDA OOM in the earlier report do not completely rule out resource exhaustion during mapping. See [Windows checkpoint I/O](../windows-checkpoint-io.md) for the source evidence and its limits.

## Retain automatic resource planning and the existing interface

AMD and NVIDIA share the automatic planning logic. Sufficient capacity still selects the resident path; streaming is used only when resources are constrained, with no new manual mode selection. BF16 weights, 8-step sampling, output dimensions, reference images, enhancement settings, history, and interaction flows retain their existing behavior.

This release does not change the pinned Python, PyTorch, or safetensors versions, or modify the bundled LightX2V source archive. Upgrades can reuse the v0.3.7 environment, models, runtime source, and workspace without deleting directories or downloading models again.

## Crash and telemetry diagnostics

- The worker enables `worker-fault.log` early to cover native faults before model-adapter imports. On successful runs, it may contain only process identity information.
- `worker-start.json` records startup and reading strategies. `worker-exit.json` records the actual exit code, hexadecimal NTSTATUS, and worker PID. Native crashes no longer display only the trailing argument JSON.
- Only existing, accessible dumps that match the PID / time are recorded. The app does not enable WER, change the registry, copy or upload dumps, or guarantee that the system will generate a dump.
- Host and stage telemetry adds run/session and producer/observed identities. Aggregation occurs only after events are successfully written to the log, with PID reuse filtered out. Commit peaks since system startup are stored separately as historical metrics.

## AMD development-machine validation

The following checks were completed on Radeon 8060S / Windows 11:

- All 135 Python checks passed, including numerical comparisons of two real official checkpoint DiT / text-encoder layers on the GPU, real GPU pread, official vocabulary-row reads, Windows DXGI, and crash diagnostics.
- Standard-library checks without third-party inference dependencies installed: 102 checks passed, with 33 dependency-specific or hardware-specific checks explicitly skipped.
- Four C# projects compiled successfully, 30 offscreen startup UI checks passed, and visual inspection of UI screenshots passed.
- Three streaming 512 text-to-image runs in separate workers, plus ordinary resident 512 generation, streaming 512 reference-image editing, streaming 1K generation, and partial-GPU prompt enhancement followed by streaming 512 generation, all produced decodable PNGs.
- The corresponding 512, 1K, and reference-image editing PNGs were byte-identical to the earlier samples.
- Streaming 512 pipeline samples on this machine took approximately 57.2–57.7 seconds, reference-image editing approximately 70.4 seconds, and 1K approximately 145.7 seconds, excluding model loading and Python startup. Resident 512 still automatically selected `full_resident`, with a pipeline sample of approximately 14.2 seconds. These are sample timings, not RTX speed promises.
- Host and worker summaries for seven actual tasks were checked field by field against the peaks, minima, and sample counts in the same sessions' JSONL logs; all matched.

Constrained-resource branches ran on the AMD development machine using budgets supplied by the test program. This does not mean that the machine actually had only an 8 GB discrete GPU / 32 GB RAM, or that cold-cache stress testing was completed.

**NVIDIA CUDA / RTX hardware retesting for v0.3.8 was still pending at release.** Start with enhancement disabled, use the same prompt and seed at 512 / 1:1, generate repeatedly, and fully exit and restart the app several times, recording at least 5 tasks. Once stable, test 1K, reference images, and enhancement. Retain the complete task directory after failures. Full 2K text-to-image generation was not rerun for this release, and the release does not claim acceptance testing of every 8 GB device or all output sizes.

Extract the entire new version into a new app folder and continue selecting the existing workspace. See [Automatic resource planning](../automatic-resources.md) for details of the logs.
